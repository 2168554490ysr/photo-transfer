### 文档分层定义

每个模块的知识分为三层。**层级之间的界限是硬性的**，不得混写。

#### L1 — 用户需求（What + Why）

描述**用户可观察到的行为契约**。回答「这个模块对外承诺做什么？」

**判定标准**：用户/产品经理能理解 → L1；删掉后功能验收会失败 → L1；只有开发者关心 → 不是 L1

**包含**：功能描述、验收条件、错误语义、模块对外状态定义

**不包含**：实现方式（线程模型/锁策略/队列类型）、库选择、具体参数值

**写作原则**：每个 REQ 只写行为契约和验收条件，不写背景解释。一个 REQ 不超过 10 行。如果发现自己在解释「为什么」→ 移到 L2

#### L2 — 架构约束（How，粗粒度）

描述**设计决策和行为策略**。回答「为什么这样做而不是那样做？」

**判定标准**：换一种实现方式需要重新讨论 → L2；违反将导致架构风险（如竞态、资源泄漏）→ L2

**包含**：线程模型、模块间通信方式、状态机转换规则、重试/退避策略、数据流向、关键设计决策及其理由

**不包含**：具体类名/函数名/变量名、具体超时数值（除非不可配置的硬编码）、代码级流程描述

**写作原则**：每个决策带理由（「X 因为 Y」），不写没有理由的陈述。如果发现自己在写代码流程 → 移到代码注释（L3）

#### L3 — 代码层（How，细粒度）

**不写独立文档**。通过代码注释、函数命名、测试用例名承载。

**包含**：库选择、参数值、实现流程、配置项说明（注释）、测试用例规格

## 变更流程
增删改需求时，遵循 `AGENTS.md`「四种工况的工作流」：
- **增加需求**：读 L1+L2 → 在 L1 追加 REQ（编号只追加不重排）→ 评估 L2 是否需变更 → 实现代码 → 测试加 @req 标签 → 验证
- **删除需求**：读 L1 → 标记 REQ 为 DEPRECATED → 删代码+测试 → 评估 L2 → 验证
- **修改需求**：读 L1+L2 → 判断变更层级（行为→L1 / 策略→L2 / 实现→L3）→ 实现 → 更新测试 → 验证
- **Debug**：直接定位修复 → 补测试（@req 关联 REQ）→ 可选补 L1

测试文件夹目前在 tests\device_manager_gui 下面。

## 分支和合并规则

### 分支类型

| 类型       | 模式      | 描述         |
| ---------- | --------- | ------------ |
| 主分支     | master    | 默认分支     |
| 开发分支   | develop   | 主开发分支   |
| 功能分支   | feature/* | 每个任务一个 |
| 发布分支   | release/* | 每个版本一个 |
| 热修复分支 | hotfix/*  | bug 修复     |

### 合并方向

| 源分支    | 目标分支 |
| --------- | -------- |
| release/* | master   |
| hotfix/*  | master   |
| feature/* | develop  |
| release/* | develop  |
| hotfix/*  | develop  |

## 提交消息指南

使用 Conventional Commits。

**格式**：`<type>(<scope>): <subject>`

**类型**：`feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`

**范围**：使用模块/目录名

**正文**：项目符号解释为什么、怎么做、影响。包含测试信息。

**示例**：
```text
fix(module): 修复某个问题

- 问题描述和解决方案

Tests: ctest -R module -V

在\docs下增加代码修改的进度和追溯矩阵，按照REQ标签，写给其他ai追寻进度用的，每一次代码更新必须更新代码修改进度与追溯矩阵。
{模块名}/tests/里面存放的是模块级的测试代码，测试完以后完善追溯矩阵
