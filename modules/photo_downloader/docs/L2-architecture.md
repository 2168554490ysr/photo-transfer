# 模块 3 — L2 架构约束

---

## ARC-01: 并发下载（4 线程）

**决策**: 用线程池（`ThreadPoolExecutor`，4 个 worker）并发下载多个文件，不再串行。

**理由**:
- 实测：同一设备上并发 `adb pull` **显著更快**（24 个文件 6.38s → 2.27s，约 2.8×）；瓶颈是每文件 `adb` 客户端/连接的往返开销（stat、握手、命令分发、进程启动），而非 USB 带宽
- 旧假设"并发会争抢导致吞吐下降"被实测推翻；USB ADB 多通道可并行，实测 4 线程已接近上限、8 线程持平
- 并发各任务的断点续传写入、进度累计需加锁保证线程安全（见 ARC-07）
- 取舍：比串行复杂，需处理进度文件并发写与错误汇总；换取显著吞吐提升

## ARC-02: 进度文件实时写入

**决策**: `.sync_progress.json` 每完成一个文件立刻 flush 到磁盘，不做批量缓冲。

**理由**:
- 断点续传的核心可靠性保证——断电/拔线后最后一个文件的进度不能丢
- 每个文件写入量约 100 字节，7000 个文件总计写入 700KB，I/O 开销可忽略
- 用 `json.dump` + `f.flush()` + `os.fsync()` 确保落盘

## ARC-03: 速度估算滑动窗口

**决策**: 传输速度基于最近 3 个文件的平均速度计算，用于"预估剩余时间"显示。

**理由**:
- 文件大小差异大（照片 3-5MB vs 视频 100MB+），单文件速度波动大
- 3 个窗口平滑了波动，但不过度滞后
- 前 3 个文件直接用瞬时速度

## ARC-04: 不完整文件检测

**决策**: 通过比较目标文件大小与清单中记录的大小判断文件完整性。不存在或大小不匹配 → 删除并重下。

**理由**:
- ADB 不支持断点续传单个文件
- 大小比对是唯一可靠的完整性检查方式（无需额外元数据）
- 中断时正在传输的文件必然不完整，大小一定小于源文件

## ARC-06: 字节级进度 + 大文件实时轮询

**决策**: 进度按**累计已下载字节**上报（通过 `on_download_progress` 的 `downloaded_bytes`）；超过 8MB 的文件在下载中后台线程拉取、主循环轮询目标文件落盘大小，实时上报字节进度。

**理由**:
- 文件大小差异大，按文件计数上报的进度不准确；字节驱动能真实反映传输进度
- 大文件下载耗时长，若仅在下完后上报，进度条会长时间停滞；轮询落盘大小实现边下边走
- 轮询在下载线程内完成，经 reporter 上报对调用方透明

## ARC-07: 并发安全与去 stat

**决策**:
- `pull_file` 接受已知 `file_size` 参数，**跳过每文件的 `stat` 往返**（原先仅用于计算超时）。`file_size` 缺失时兜底 stat。
- 并发下载中，进度文件写入（`_update_progress`/`_save_progress`）、`downloaded_bytes` 累计、`success/failed/errors` 汇总均通过一把全局锁保证线程安全。

**理由**:
- 每文件一次 stat 往返实测 ~84ms；7000 文件仅 stat 就 ~9 分钟，删除纯属浪费（+26%）
- 并发下多个线程同时写进度文件会丢失/损坏记录；锁将"读-改-写"串行化，保证断点续传可靠（沿用 REQ-04 契约）
- 锁粒度细（每次进度写入/计数），不阻塞并行下载本身

---

## ARC-05: 同步日志追加模式

**决策**: `.sync_log.json` 记录每次完整同步的摘要，使用数组格式追加。

**理由**:
- 用户可回溯历史同步记录
- 日志文件体积不会无限制增长（每次一条记录，约 200 字节）
- 不用于程序逻辑决策（进度文件 `.sync_progress.json` 负责），仅用于人工查看
